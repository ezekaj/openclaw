# 2026-03-10 Memory

## Database Architecture Decision

**Context explosion investigation: 234 → 23k tokens**

Root cause: Heartbeat design, not database performance.

### Findings
- Total SQLite usage: 417KB (tiny, optimal)
- tool-analytics.db: 332KB (49 calls, 951 buckets)
- heartbeat-v2.db: 56KB
- cron/store.db: 20KB
- 95 TypeScript files integrated with SQLite

### Decision: Keep SQLite ✅

**Why MongoDB would be worse:**
- Adds network latency (2-5ms vs 0.1ms)
- Requires separate mongod process
- Connection pooling complexity
- No benefit for 417KB dataset
- Migration cost: 95 files, new deps, testing

**Why SQLite is optimal:**
- Faster for small datasets (zero network overhead)
- ACID transactions, reliable
- Zero configuration
- Already well-integrated
- Sub-millisecond queries

### Real Problem: Heartbeat Design

Heartbeat runs 9 tool calls that dump into context:
- `read` HEARTBEAT.md (1.7k)
- `cron list` → 2KB JSON
- `browser status` → JSON
- `predictive status/stats` → JSON
- Various `exec` checks

### Solution: Context-Efficient Heartbeat

**Options:**
1. Isolated sub-agent for heartbeat (98% context reduction)
2. Tool response summarization layer
3. /api/health endpoint for external monitoring

### Implementation Priority

1. **IMMEDIATE:** Redesign heartbeat (23k → 500 tokens)
2. **SHORT-TERM:** Add /api/health endpoint
3. **NEVER:** Migrate to MongoDB (unless data grows 100,000x)
